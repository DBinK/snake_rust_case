# 04 完整实现：领域逻辑与工程落地

在完成第 03 章的终端交互原型后，本章将构建完整的贪吃蛇游戏。项目由三个模块构成：

- `src/game.rs`：纯领域逻辑层（状态机、坐标计算、移动碰撞与单元测试）。
- `src/terminal.rs`：终端适配层（RAII 守卫、非阻塞事件轮询、屏幕绘制）。
- `src/main.rs`：应用编排层（状态机驱动与动态节拍主循环）。

运行完整版游戏与单元测试：

```bash
cargo run
cargo test
```

## 核心机制深入剖析

### 1. 状态机与非法状态消除（`src/game.rs`）

游戏阶段建模为状态机枚举：

```rust
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum Phase {
    Ready,
    Playing,
    Over,
}
```

在 `Game::turn` 与 `Game::step` 中，这一状态机充当业务护栏：

```rust
pub fn turn(&mut self, dir: Dir) {
    match self.phase {
        Phase::Ready => {
            self.dir = dir;
            self.phase = Phase::Playing;
        }
        Phase::Playing => {
            if dir != self.dir.opposite() {
                self.dir = dir;
            }
        }
        Phase::Over => {}
    }
}

pub fn step(&mut self) {
    if self.phase != Phase::Playing {
        return;
    }
    // ...
}
```

- Ready 阶段收到的方向按键直接作为游戏起步方向，并自动切换为 Playing。
- Playing 阶段严格拦截 180 度反向操作。
- `step` 仅在 Playing 阶段推进。调用者无需在外部记忆“何时可以推进”，领域对象自身守住这一不变式。

### 2. 借用检查机制在 `Game::step()` 中的体现

`Game::step()` 是整个项目中借用检查最为集中的函数：

```rust
let next = self.next_head();
let hit_wall = next.x >= WIDTH || next.y >= HEIGHT;
let will_grow = next == self.food;

let mut body = self.body.iter().copied();
if !will_grow {
    body.next_back();
}
let hit_self = next == self.head() || body.any(|p| p == next);

if hit_wall || hit_self {
    self.phase = Phase::Over;
    return;
}

self.body.push_front(next);
if will_grow {
    self.score += 1;
    self.place_food();
} else {
    self.body.pop_back();
}
```

#### 为什么使用 `body.iter().copied()`
在判断蛇头是否撞到自身时，若未吃到食物，尾节点即将在本轮移出，因此需要排除尾节点后再做重叠比对。
- 如果将 `self.body` 复制为一个新的容器（如 `Vec`），会产生不必要的堆内存分配与数据拷贝。
- `self.body.iter().copied()` 产生的是一个双端轻量迭代器。调用 `body.next_back()` 可以在不修改原始双端队列的前提下，从迭代视图末尾排除掉尾节点。

#### 借用检查的时间线约束
在 Rust 中，同一块数据在同一时间只允许存在一个可变引用，或多个不可变借用。
若先执行 `self.body.push_front(next)`（可变借用），后续就无法再安全地借用迭代检查咬身情况。
借用检查器要求开发者：**先完成所有的不可变状态读取与条件计算，最后再执行可变状态的变更**。这不仅是语法的硬性约束，更是清晰排布软件因果逻辑的优秀实践。

### 3. 边界碰撞检测与回归测试

注意这行判定：
```rust
let hit_self = next == self.head() || body.any(|p| p == next);
```

#### 为什么需要 `next == self.head()`？
在 `next_head` 中，由于坐标类型采用 `u16`，向上或向左移动时使用了 `saturating_sub(1)`：
- 当蛇头位于边界 `x = 0` 并继续向左移动时，`saturating_sub` 会将坐标钳制在 `0`，使得计算出的 `next` 依然等于 `head`。
- 如果蛇身长度仅为 1 节（未吃到食物），由于 `!will_grow` 会剔除唯一的尾节点（即当前头节点），此时单纯依赖 `body.any(...)` 将无法检测到原地踩墙，导致蛇贴在边界原地踏步且永不死亡。
- 通过显式补充 `next == self.head()`，贴墙原地受阻的情形被准确判定为死亡。

在 `src/game.rs` 末尾，我们编写了针对此场景的回归测试用例：

```rust
#[test]
fn dies_when_pinned_to_edge() {
    let mut g = Game::new();
    g.turn(Dir::Left);
    for _ in 0..WIDTH {
        g.step();
    }
    assert!(matches!(g.phase, Phase::Over));
}
```

### 4. 基于 RAII 的确定性资源清理（`src/terminal.rs`）

针对第 03 章手动恢复终端的隐患，`terminal.rs` 引入了 RAII 资源守卫：

```rust
pub struct RawMode;

impl RawMode {
    pub fn enter() -> io::Result<Self> {
        terminal::enable_raw_mode()?;
        crossterm::execute!(io::stdout(), terminal::EnterAlternateScreen, cursor::Hide)?;
        Ok(RawMode)
    }
}

impl Drop for RawMode {
    fn drop(&mut self) {
        let _ = crossterm::execute!(io::stdout(), cursor::Show, terminal::LeaveAlternateScreen);
        let _ = terminal::disable_raw_mode();
    }
}
```

在 `src/main.rs` 开头，仅需一行声明：
```rust
let _guard = RawMode::enter()?;
```
无论主程序是正常退出、遭遇 `?` 提前返回还是发生非预期异常，当 `_guard` 离开作用域时，Rust 运行时都会确定性调用 `drop` 方法，确保终端显示与输入模式完整恢复。

### 5. 代数数据类型与非阻塞输入轮询

```rust
pub enum Input {
    Move(Dir),
    Quit,
    Retry,
}

pub fn read_input(timeout: Duration) -> io::Result<Option<Input>>
```

- 将按键结果抽象为 `Option<Input>`。
- 变体 `Input::Move(Dir)` 携带具体的方向数据，类型系统杜绝了数据与操作类型脱节的可能。
- `Option` 明确将“在指定超时内未按下按键”表述为合法状态，强制外层主循环显式匹配。

### 6. 主循环编排（`src/main.rs`）

```rust
let mut g = Game::new();
loop {
    draw(&g)?;
    match g.phase {
        Phase::Ready => match read_input(Duration::from_secs(3600))? {
            Some(Input::Quit) => break,
            Some(Input::Move(d)) => g.turn(d),
            _ => {}
        },
        Phase::Playing => {
            match read_input(tick_for(g.score))? {
                Some(Input::Quit) => break,
                Some(Input::Move(d)) => g.turn(d),
                _ => {}
            }
            g.step();
        }
        Phase::Over => match read_input(Duration::from_secs(3600))? {
            Some(Input::Quit) => break,
            Some(Input::Retry) => g.reset(),
            _ => {}
        },
    }
}
```

主循环结构清晰展示了状态机的威力：
- Ready 与 Over 阶段无需定时器驱动，直接挂起长超时等待玩家操作，极大降低 CPU 占用。
- Playing 阶段采用 `tick_for(score)` 作为超时周期，实现平滑的动态加快速率控制。

### 7. 可测试性设计

由于 `Game` 与终端 I/O 完全解耦，所有单元测试均能毫秒级运行，无需模拟终端环境或 Mock 复杂的输入接口。这是良好分层架构带来的直接收益。
